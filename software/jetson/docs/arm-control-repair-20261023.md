# 机械臂无响应诊断与启动提示修复

2026-10-23，Asia/Shanghai。

## 实测结果

USB CH340 控制板位于 `/dev/ttyUSB0`；驱动复位保护为 `Y`，打开串口未出现启动广播，
`$GETA!` 返回 `AAA`。000 号舵机返回 P1504，版本为 `ZL-ZServo_AD_CBM V2.1.16STG`。
001～005 号的两轮位置查询均只收到 `PRAD` 查询回显。单次等待延长至 700 ms 后，
这些关节的位置与版本查询仍都只有回显；不能把回显当作舵机反馈或连接成功。

用户确认独立电源已开，未修改接线或舵机 ID。厂家本地接线资料说明六路舵机串联，
因此需要优先检查 000 与 001 之间总线、后续供电及连接。当前数据不能确定具体坏件，
也不能证明五个舵机都已损坏。本轮未发送运动目标、改写舵机 ID、设置模式或放宽限位。

本轮启动前相机与识别服务运行，跟随服务未运行；相机画面中也未检测到目标碗。
昨日的跟随状态文件不是当前连接证明。

## 软件修改

- `ArmSerial.positions()` 汇总六路实测位置和缺失回复；复位、外部动作等异常仍立即中止。
- 启动准备先检查控制板及六路反馈，再等待新目标，避免无碗时掩盖总线故障。
- GUI 保留具体的启动故障及运行故障；分段 UTF-8 输出也能正确显示中文。
- 服务即使收到 `state=stopped`，仍立即报告其中的故障，不等待启动超时。
- 增加无运动目标的独立检查工具：

```bash
./.venv/bin/python tools/check_arm_connection.py
```

工具只在唯一 CH340 存在时自动选择端口，检查握手、六路位置并在退出时发送停止。
报告默认保存为 `work/arm-small-test/connection-status.json`。`ready=true` 只表示六路位置可读，
不表示已验证机械动作、当前姿态或视觉标定。

## 验证记录

原始查询在 `work/control-repair-20261023/bus-check.json` 和 `slow-servo-check.json`。
修改前源文件副本在同目录的 `before/`，离线回归结果在 `tests.log`。
108 项离线测试通过，已更新运行中的视觉界面。用户重新插紧 000→001 两端并上电后，
`after-reseat.json` 记录仍只有 000 反馈；物理链路故障尚未恢复。
需要线缆检查后重新取得全部关节位置，才能继续核对姿态与目标并验证跟随。

## 最终恢复情况

随后用户进行了接线检查；期间控制板 USB 曾断开。重新连接 USB 后，六路位置均可读，
记录为 `shoulder-bypass-reconnected.json`：000=1510、001=1491、002=2057、003=1489、
004=1492、005=1545。用户确认最终已经恢复正常串联。
通信恢复与接线检查、USB 重连发生在同一轮排查，不能据此断言具体某根线或舵机损坏。

新姿态超出昨日局部跟随标定范围，保持关节也偏离昨日参考。用户明确要求
“先只修复连接，暂不恢复跟随”。因此本轮仅确认连接与位置反馈恢复，保持停止，
未试动、未重新标定、未启动跟随服务，也未扩大旧配置范围。
最终连接报告保存在 `work/arm-small-test/connection-status.json`，须按其检查时间判断时效。
