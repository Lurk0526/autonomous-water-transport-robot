# 机械臂串口复位修复记录

日期：2026-10-21，Asia/Shanghai。

## 结果与当前状态

串口打开时反复出现启动/全舵机回中信息的问题已在当前 Jetson、内核与控制板组合上修复。修复后多次开关串口没有再收到启动广播，握手得到 `AAA`，六个关节的实测位置可读，停止得到 `#255PDST!` 回显。

用户明确接管条件：已松开遥控器、由电脑接管。此前收到的 `#000P2400T2000!` 是用户操作遥控器产生；检测到位置变化后程序已停止，并没有把外部动作算成本程序试动成功。

当前磁编码舵机版本是 `ZL-ZServo_AD_CBM V2.1.16STG`，旧手册 `#000PMOD!` 仅返回查询回显，没有工作模式值。后续已为该确切版本接入厂家的磁编码位置控制例程核验路径；继续如实记录 `mode_confirmed=false`，不设置或伪造模式。其他未知型号及明确的连续转动模式仍拒绝试动。

最新进展：底座两轮 +10 P 测试没有测得位置变化，不能记为运动成功；004 号相对 +30 P 的实测为 1496→1518→1503，用户没有看清，因此只记反馈有变化。随后按用户要求调整 003 腕部，实测 1507→1455，用户确认看到了少量低头。

用户进一步要求接近 90°低头并确认可以加快。程序从当时新测的 P1493 分段降低，最终到 P992；前段每 100 P/2 秒，后段每段约 1 秒。每段后都核对位置、其他关节和新相机图像。相机画面从上方转到前方，已停止并保持新姿态；尚无机械角度标定，不能把 501 P 直接宣称为精确 90°。

实时采图、分割和 Isaac 已恢复，约 18 FPS；运动跟踪尚未开启，正在等目标碗放稳后进行局部方向/响应校准。

## 原因与修复

厂家核心板原理图中的 CH340K DTR/RTS 连接至 STM32 的自动下载/复位电路。旧应用把两根线预设为 False，但 pySerial 在 open 中先后设置 DTR 和 RTS，内核也会在打开串口时配置这些信号。两根线分阶段改变可能短暂出现触发复位的组合。

先尝试用户态同时设置，两次实测分别仍出现握手失败或启动广播，说明仅修改应用不足。最终在原有 Linux stable v6.8.12 的 CH341 驱动上添加可选的 `jibot_no_auto_reset` 参数：启用时，仅对 USB `1a86:7523` 强制两根控制线保持不触发下载/复位的非活动状态，覆盖内核 open、termios 和 modem ioctl 的信号更新。读取 modem 状态也反映实际被强制的控制线状态。

当前配置：

- 内核：`6.8.12-1021-tegra`。
- 模块：`/lib/modules/6.8.12-1021-tegra/updates/ch341.ko`。
- 持久化选项：`/etc/modprobe.d/jibot-ch341.conf`，`options ch341 jibot_no_auto_reset=1`。
- 运行状态：`/sys/module/ch341/parameters/jibot_no_auto_reset` 为 `Y`。
- 项目补丁：`drivers/ch341-jibot-no-auto-reset.patch`。
- 原模块备份：`work/arm-small-test/driver-fix/original-ch341.ko`。
- 修改后的模块 SHA256：`0b6f64d88b35ad0d9baf35ea812d9f46973ed0f8901b0bb236edb34bef89896f`。
- 原模块 SHA256：`5c3d13066d88ad25589aa70549ee6b89cdefdb94f454730c1ab35de4bb05b0a9`。

当前只连接了一块该 USB ID 的 CH340。该选项也会影响以后接入的其他同 ID CH340 设备的 DTR/RTS，普通收发继续可用，但依赖这些信号的自动下载/流控不可用；其他 USB ID 保持原驱动行为。本次未改写 STM32/OpenMV 固件、舵机 EEPROM、位置偏差或模式，也未运行全臂动作组。

## 应用保护

`vision/arm_serial.py` 在打开控制板之前检查驱动保护是否启用。保护缺失（例如内核升级后没有重新安装）时直接拒绝开串口，不再以普通驱动反复重试。用户态同时设置信号的逻辑继续保留。

启动广播检测、CH340 端口隔离、位置反馈、限位、停止等检查全部保留。新增检查会区分本程序运动指令的回显与未授权来源的运动指令，后者引发停止与中止。

驱动保护并不消除硬件断电、USB 故障、外部遥控器或控制板固件自身的动作；只解决已定位的串口控制线问题。后续试动仍需有效协议识别和当前姿态核对。

当前已识别的 CBM 固件采用受限单关节调试路径：同时核验确切 PVER 回答和厂家磁编码动作文件 SHA256 `9d8cb501fb3ab64aaad7d41025d18598c292acf1f9610993adc7b6a1d60f98a1`。这份原厂文件明确使用 P/T 位置控制格式。首次小幅测试只准许底座 10 P 或历史测试过的末端旋转 30 P；低头/俯仰分段工具由用户的额外姿态指令授权，独立限制每段最多 100 P、每次会话最多 500 P。

串口增加至少 50 ms 的指令间隔，查询只有两次有界尝试。端点查询与定时运动分开，运动阶段仍持续接收并检查复位或外部运动指令，完成后再读位置。厂商的 UART 桥会转发查询与反馈；目前未证明频繁查询就是底座 10 P 无响应的原因，也未根据这个推断扩大底座范围。

## 构建与回退

原始驱动来源、校验值和构建记录在 `work/arm-comm-check/ch341/`；修复后的源码、Makefile 与模块在 `work/arm-small-test/driver-fix/`。仅适用于当前内核。换内核需使用对应头文件重建并重新验证；应用会在保护不可用时停止。

如需要恢复自动下载能力，先停止一切串口应用，确保机械臂可安全承受原来的复位/回中行为，再恢复备份模块与原 modprobe 配置。不要在串口被占用或机械臂运动时卸载驱动。回退后项目保护检查会阻止继续用普通串口路径运行机械臂控制，直到重新处理控制线行为。
